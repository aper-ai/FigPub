# 性能实测与解释

本报告第 1–6 节保留 0.1/0.2 的历史测量；最后一节记录 0.3 的新增工作流。历史部分记录 0.2.0 的多通道与 Cellpose 测量，并保留 0.1.0 的四项核心基线。第 1–4 节是历史基线，本轮没有将它们重新计时；第 5–6 节是本轮新增实测。全部输入是可重建的合成数据，完整参数、逐次耗时及限制保存在 `benchmarks/*.json`。机器是 Linux x86-64、Intel Xeon Platinum 8573C；Python 3.12.14，Node 24.22.1。单项测试在不同时间运行，负载可能不同。

**没有对原 GelFigure / ScieFig 应用做同机全流程 A/B，也没有真实实验图像准确率基准。因此这些数据不支持“整体快若干倍”或“行业领先”的宣称。** 它们验证的是可解释的结构改进，以及新实现本身的耗时。

## 1. WB：先裁 ROI，再转 float64

输入为 4096×4096、uint16 图像，24 个 128×48 ROI。两种实现计算相同的边缘中位数背景和有符号净积分，逐 ROI 数值完全一致。

| 路径 | 中位耗时 | p95 | 转为 float64 的数值数 |
|---|---:|---:|---:|
| 新核心：先取 ROI 再转换，5 次暖调用 | 5.24 ms | 5.65 ms | 147,456 |
| 人工构造的朴素对照：每个 ROI 重复转换整图，5 次 | 779.30 ms | 1,097.86 ms | 402,653,184 |

新核心第一次调用为 12.22 ms。原始 dtype 仍为 uint16，原图字节未改变。这个对照故意暴露“每 ROI 重复转换整图”的开销，**不是对原软件的计时**。原始结果：[results_core.json](../benchmarks/results_core.json)。

真实 rolling-ball 是另一种更昂贵的背景模型，不能借用中位数背景的耗时作宣传。256×384、radius=12 的单次合成测量约 137.42 ms；半径、图像大小和数据类型会显著影响耗时。

复现：

```bash
python benchmarks/benchmark_core.py
```

## 2. 凝胶定位：有界预览与线性投影

此项只测新定位引擎。数据构造在计时外，暖调用 7 次；不包括 HTTP、Worker 启动、目录匹配和人工校准。

| 合成定位输入 | 预期 / 检出的泳道 | 检出的条带 | 暖调用中位数 | 本组最大值 |
|---|---:|---:|---:|---:|
| 640×360 | 6 / 6 | 24 | 23.10 ms | 51.48 ms |
| 1024×1024 | 12 / 12 | 48 | 59.68 ms | 68.33 ms |

第一次调用分别为 67.52、66.01 ms。定位任务运行在 Worker，不在 UI 线程执行图像算法。所有位置会映射回原始像素；它们仍是待核对的检测候选，不能把合成数据的检出数量当作真实数据准确率。[results_gel.json](../benchmarks/results_gel.json)

```bash
node benchmarks/benchmark_gel.cjs
```

## 3. 定位像素：二进制与 JSON

从 4096×4096 uint16 原图生成同一个 1024×1024 定位视图，缓存命中后通过 FastAPI 内进程 TestClient 测量响应序列化。两条响应逐个 float32 数值一致。

| 响应形式 | 响应字节数 | 5 次暖调用中位耗时 | p95 |
|---|---:|---:|---:|
| little-endian float32 | 4,194,304 B（4 MiB） | 7.92 ms | 11.22 ms |
| JSON 数值数组 | 20,119,328 B（约 19.19 MiB） | 1,176.38 ms | 1,230.88 ms |

这包含框架序列化的开销，不是互联网速度或浏览器帧率测试。首次二进制调用含原始解码/缩小等步骤，约 109.45 ms。前端使用 `ArrayBuffer`，并通过 transferable buffer 交给 Worker；定量仍读取原始 uint16。[results_transport.json](../benchmarks/results_transport.json)

```bash
python benchmarks/benchmark_transport.py
```

## 4. 撤销：只保留编辑配方

合成工程含 1,000 个对象、每对象 128 个轮廓点，用来模拟较大的分析结果。编辑配方不包含已完成结果、原始资产与审计历史。

| 项目 | 实测 |
|---|---:|
| 完整工程序列化大小 | 4,917,230 B |
| 单份编辑配方序列化大小 | 492 B |
| 100 次配方快照中位耗时 | 0.025 ms |
| 配方快照 p95 | 0.113 ms |
| 深复制完整工程一次的参考耗时 | 226.46 ms |

**序列化大小不是进程堆内存占用。** 完整复制只测了一次，不能据此推导稳定加速比。测试的主要结论是：撤销栈不会因为保存了大型不可变分析结果而重复携带这些结果；上限为 60 个配方快照。[results_frontend.json](../benchmarks/results_frontend.json)

```bash
node --expose-gc scripts/benchmark_frontend.mjs
```

## 5. 多通道：逐平面处理与原始数据保持

输入为 4×2048×2048、CYX、uint16 的 Deflate TIFF，压缩文件约 30.0 MiB。合并使用四通道；分屏为四个单通道及一个合并图，三列排列、原始像素间距为 8。每组单独启动进程进行一次冷应用缓存测量，再执行两次原始平面缓存已命中的暖调用。

| 场景 | 输出像素 | 首次渲染 | 暖渲染中位数 | PNG 编码（另计） | 采样到的最高 RSS |
|---|---:|---:|---:|---:|---:|
| 合并预览 | 1024×1024 | 659.97 ms | 224.94 ms | 81.21–88.22 ms | 147.6 MiB |
| 原尺寸合并 | 2048×2048 | 490.50 ms | 163.83 ms | 未计 | 159.1 MiB |
| 分屏预览 | 1024×682 | 153.32 ms | 45.16 ms | 43.89–45.19 ms | 99.5 MiB |
| 原尺寸分屏 | 6160×4104 | 944.92 ms | 499.77 ms | 未计 | 287.4 MiB |

这里的“冷”指新进程及空应用平面缓存，**没有清空操作系统文件缓存**；“暖”没有命中最终 PNG HTTP 缓存。RSS 每 5 ms 采样，可能遗漏更短的峰值；表中是整个测量进程的峰值，不是应用额外内存，也不是完整浏览器加服务器的总内存。两次暖测量只能作为本机参考，不能代替性能分布。

渲染每次只展开一个来源平面并应用 LUT；原尺寸 LUT 以约 262,144 像素的小块计算，超过 800 万像素的浮点 RGB 累加器使用临时映射文件。四个原始平面均保持只读 uint16，渲染前后文件及每个原始平面的 SHA-256 一致。原始 plane 缓存命中和最终 PNG 缓存是两个独立层，不会用缓存的 8 位显示图进行科学定量。

完整参数、逐次时间和采样内存：[channels_results.json](../benchmarks/channels_results.json)。复现：

```bash
python benchmarks/bench_channels.py
```

## 6. Cellpose：实际 CPU 组件执行

独立组件使用 Cellpose 3.1.1.3、Torch 2.7.1+cpu 与官方 nuclei/cyto3 权重。输入是 160×192 uint16、六个高斯亮斑的合成图；固定 2 个线程，Numba 使用 `workqueue`。每个模型实际启动独立进程，包含导入、模型初始化和推理。

| 模型 | 返回候选数 | 进程内推理 | 含进程启动墙钟 |
|---|---:|---:|---:|
| nuclei | 6 | 1,068.88 ms | 8,431.14 ms |
| cyto3 | 6 | 1,787.74 ms | 8,453.95 ms |

每个模型仅记录一次，计时不包含科学准确率评估。原始数组保持不变，返回坐标位于原图范围；这说明权重及执行链能运行，**不证明真实细胞分割准确率或 Windows 上的耗时**。完整记录和复现脚本分别为 [cellpose_cpu_smoke.json](../benchmarks/cellpose_cpu_smoke.json) 与 [smoke_cellpose_cpu.py](../benchmarks/smoke_cellpose_cpu.py)。

## 7. 交互、渲染与成本边界

拖动仅更新活动 SVG 对象，松手后提交一次历史记录；自动保存串行执行。有界缓存限制常驻图像/预览/定位/表格及 SVG 转换结果，字体派生也有预算。多通道 HTTP 预览缓存最多 48 项、48 MiB，等价并发请求复用同一个任务；同时渲染最多 2 项，待处理不同配方最多 8 项，超过时返回可重试的 429。前端保留最新请求、释放废弃 Blob，并对忙碌响应做有限重试，已取消的请求不会重新发起。缓存和内存映射能减少重复工作，但不能消除大图解码与导出所需的真实内存。

图表和 PDF 的第一次中文导出可能需要生成字库缓存/子集；后续可重用。CPU 分割及 rolling-ball 有实际计算成本。普通线程内数值任务使用软取消，已进入原生调用的工作会在返回后释放线程，取消后不能写入结果。Cellpose 单独运行在进程中，导入、模型初始化和推理阶段均可由取消或超时终止；这与普通线程任务的取消机制不同。

真实浏览器功能流程和独立 SVG 渲染误差见 [VALIDATION.md](VALIDATION.md)。浏览器流程耗时包含人机操作模拟、自动保存等待、文件下载等，未作为算法速度排名。

## 下一轮性能评估应怎样做

要证明超越原项目，需要另建获得授权的真实凝胶、WB、显微图与仪器表格集合，固定两套上游提交、同一硬件和相同任务；分别比较冷启动、稳态交互、峰值内存、分析数值一致性、导出质量和失败率。定位/分割应有人工真值及误差分布，不能用“界面更快”替代科学准确性。

这些是进一步下结论所需的证据，不是当前版本已经完成的评估。


## 7. 0.3 本轮高级工作流实测

源码：[benchmark_workflows.py](../benchmarks/benchmark_workflows.py)；完整原始记录：[workflows_results.json](../benchmarks/workflows_results.json)。每组一次预热和五次计时，输入只读；每次校验结果正确性、参数与原件 SHA 不变、排除耗时后的结果确定性。

| 后端工作流 | 输入 | 中位耗时 | 五次范围 |
|---|---|---:|---:|
| 多曝光质量推荐 | 12 张 512×768 uint16，144 ROI，24 身份，3 曝光 | 14.176 ms | 13.731–15.735 ms |
| 固定 H/DAB＋人工分级 | 1024² uint8 RGB | 55.809 ms | 52.108–92.902 ms |
| Macenko＋人工分级 | 同一 1024² RGB | 68.151 ms | 64.560–73.193 ms |
| 纤维形态、核归属与标记 | 1024²，64 纤维，208 核，4 平面 | 493.760 ms | 440.026–510.500 ms |
| 修改纤维标签后完整重算 | 1024²，65 纤维，208 核 | 410.185 ms | 388.464–431.791 ms |
| 两实例 split＋merge 重放 | 1024²，2→3→2，精确恢复原标签 | 74.092 ms | 70.073–107.233 ms |

IHC 的 984064 个组织像素四级计数与合成真值一致，Macenko 实际运行并使用 98407 个确定性样本。纤维全部 208 核纳入记录，192 核正确归属、16 核在纤维外；标签修改后归属与对应指标同步更新。WB 弱信号与削顶曝光均被拒绝，建议没有自动应用。

环境为 Linux、AMD EPYC、9 个可见 CPU，过程内线程请求为 1；共享主机无独占保证，1 分钟负载 0.43848→0.52539。上述时间是已加载数组上的后端计算，不含解码、HTTP、GUI、导出或 Windows 执行，不是整个操作流程的完成时间。对象数量、轮廓复杂度、原图噪声与内存会影响实际速度。

主要效率措施是 ROI 局部计算、向量化/分块 OD、最多 100000 样本的染色估计与 GMM、凸包卡尺、有界轮廓/标签、原图只读与小型操作重放。没有同机上游对照数据时不作领先排名。
